# Decisions

Source: [brief.md](brief.md). Findings: [brief-review.md](brief-review.md). One row per choice. `product` = what to build or cut. `tech` = how to build it.

## 2026-10-17 - v1

| # | Kind | Decision | Why | Alternatives considered | Consequence |
|---|---|---|---|---|---|
| 1 | product | Production-grade build. | **F17.** The system serves as a reference implementation. It must meet production standards for reliability, security and observability. | **Prototype scope (no auth, logs only):** faster, but leaves the operational concerns undemonstrated. | Correctness, failure handling and tests meet production standards from v1. Cloud deployment comes later, see #16. |
| 2 | tech | Transactional outbox in Recording and Segmenter. The state change and the outbox row go in one DB transaction. | **F1.** A crash between commit and publish loses the event. The activity is stored but never scored. | **Publish after commit:** loses the event on crash. **Emit a second event to a checker:** that emit can fail too, so the same gap remains. **Publish inside the transaction:** a DB transaction cannot cover Pub/Sub. A rollback after publish leaves a phantom event. **CDC (Debezium):** no gap, but extra infra to run. Kept for v2. | Each service has an `outbox` table in its own schema. Delivery is at-least-once, and #4 covers repeats. |
| 3 | tech | The relay runs as a separate process from the same image (`recording-relay`, `segmenter-relay`), one instance per service. It loops: select unsent rows in outbox `id` order, publish with ordering key `merchantId`, wait for ack, mark sent. | **F1, F8.** It restarts on its own, and the API request path stays free of publish work. Pub/Sub orders by arrival, so per-merchant order must be fixed before publish. One relay reading by `id` does that. | **Background task in the API process:** simpler, but an API restart pauses publishing. **Several relays with `SKIP LOCKED`:** two relays can publish one merchant's rows out of order. **Several relays, each owning a `merchantId` hash range:** keeps order and scales, but needs partition assignment. Kept for v2. **CDC:** see #2. | Two more containers. Throughput is capped at one relay per service. A crash after ack and before mark-sent publishes again, and #4 absorbs it. Pub/Sub down: rows pile up and go out once it is back. |
| 4 | tech | Consumers are idempotent on `eventId`. Each consumer keeps a processed-event table in its own schema, written in the same transaction as the state change. | **F7.** Pub/Sub and the relay both deliver at-least-once. | **In-memory dedup:** lost on restart. **No dedup:** a repeat double-counts a chargeback. | A redelivered event is acked and changes nothing. |
| 5 | tech | `ActivityRecorded` carries the full fact: `eventId`, `activityId`, `merchantId`, `type`, `occurredAt` and the type's payload. | **F2.** Segmenter must never call Recording. | **Thin event + callback over HTTP:** Segmenter goes down when Recording does. That breaks the brief. | The event schema is a contract. Changes must be additive. |
| 6 | tech | Segmenter keeps its own copy of the facts its rules read: one row per fact (`merchantId`, `type`, `occurredAt`, `eventId`), pruned after the longest policy window. | **F2.** Rules need the past ("3 chargebacks in 30 days"). One event holds only the present. | **Counts in the event from Recording:** Recording would own policy windows, so a rule change means a Recording change. **Full history in each event:** events grow without limit. **Daily counters:** smaller, but windows round to whole days and dedup is harder. **Read Recording over HTTP:** couples their uptime. | The copy is derived. It can be rebuilt by replaying events. It is not a second system of record. |
| 7 | product | No time-based decay in v1. A band changes only when an event arrives. | **F5.** Decay needs a scheduler, because no event triggers it. Out of scope for v1. | **Scheduled decay job:** a new trigger and new tests. Kept for v2. **Decay checked on the next event:** the band stays stale until something happens. Confusing for risk teams. | A merchant can stay `high` until a rule lowers it on a new event. |
| 8 | tech | The client sends `activityId`. Recording enforces it with a unique constraint. A repeat creates no new row and no new event, and returns the original result. | **F3.** Client retries must not double-count a chargeback. `eventId` dedup covers consumers only. | **`Idempotency-Key` header + response cache:** more state to keep and expire. **Server-generated id:** every retry is a new activity. | `activityId` is required on `POST`. |
| 9 | tech | Pub/Sub ordering key = `merchantId`. The segment row also carries a version number, checked on update. | **F4.** Events for one merchant must be evaluated in order. Several Segmenter instances must not overwrite each other. | **No ordering:** the band can be computed from facts out of order. **Ordering only:** redelivery and rebalancing can still overlap. **Row lock only:** safe writes, but the order stays random. | Throughput is serialised per merchant. That is fine at this volume. |
| 10 | tech | Each subscription has a dead-letter topic, used after 5 failed attempts. An alert fires on dead-letter depth. | **F6.** With ordering keys, one poison message blocks every later event for that merchant. | **Retry forever:** that merchant's segment freezes. **Drop on failure:** silent loss. | A dead-lettered event needs a manual replay path. |
| 11 | tech | Segmenter serves `GET` segment. Notifier serves `GET` alerts. Each gets its own HTTP entrypoint. | **F11.** Each service reads only its own schema. | **Recording serves all reads:** it would read other schemas. **Separate query service:** not needed for three services. | Clients call three services. A gateway can be added later. |
| 12 | product | v1 alert = a stored row in `notifier` plus a structured log line. No email or Slack. | **F12.** It proves the event path end to end. Delivery channels add no design risk. | **Email / Slack now:** secrets and vendor mocks. Kept for v2. | The delivery adapter sits behind a port, so v2 adds a channel without touching the handler. |
| 13 | tech | A new policy version applies from the next event. The segment row stores `policyVersion`. | **F13.** Every decision stays explainable: the band, the version and the facts. | **Re-score all merchants on release:** a batch job and an alert storm. | Merchants with no new events keep the band from the older version. |
| 14 | product | A merchant is created on its first activity and starts at `low`. | **F14.** There is no merchant service in scope. | **Require registration first:** needs a merchant service, which is out of scope. | Any `merchantId` is accepted. Checking it against a merchant registry is a v2 concern. |
| 15 | tech | Python, FastAPI, SQLAlchemy, pytest. | **F16.** It matches the brief's layout (`domain`, `service_layer`, `adapters`, `entrypoints`). | **TypeScript / Node:** fine, but the brief is already shaped for Python. **Go:** more boilerplate for the same result. | One toolchain for all three services. |
| 16 | tech | v1 runs on Docker Compose only: Postgres, Pub/Sub emulator, three services, two relays. | **F17.** v1 proves the design. Cloud infrastructure adds cost and credentials, but no design risk. | **Cloud Run + Terraform in v1:** a real deployment, but slower to iterate and needs a GCP project. | Deploy target, IaC, IAM auth and tracing move to v2. The Pub/Sub adapters target real GCP by configuration only. |
| 17 | product | Policy v1 rules: chargeback 1 in 30d -> `medium`, 3 in 30d -> `high`. Velocity breach 2 in 7d -> `medium`. KYC expired -> `high`. Failed login 10 in 1h -> `medium`. Otherwise `low`. | **F9.** Simple thresholds are easy to explain to risk and compliance, and easy to test at each boundary. | **Weighted score per type:** finer grained, but harder to explain. A candidate for a later policy version (#13). | Every rule needs a test just below, at and above its threshold. |
| 18 | product | The band never drops automatically. When a recompute gives a lower band, Segmenter keeps the current band, opens a risk check and emits `ManualRiskCheckRequired`. A rise applies at once. No activity type lowers risk in v1. | **F5.** A drop caused only by facts leaving their window is not a risk decision. A human confirms it. | **Recompute and drop:** fully automatic, but the drop is triggered by an unrelated event, so its timing looks arbitrary. **Sticky band, no check:** windows only work upward, and nothing ever lowers a band. **Add `kyc_renewed` now:** kept for v2. | One open check per merchant. Another lower recompute while a check is open emits nothing. A rise closes the open check. With no scheduler (#7), a check is raised only when an event arrives. |
| 19 | product | When several rules fire, the highest band wins. | **F10.** It is the conservative choice for a risk system. | **Most recent rule wins:** the result depends on event order. **Sum of rules:** needs weights, see #17. | The segment stores which rule set the band, for explainability. |
| 20 | tech | A CLI command republishes dead-lettered messages after a fix. | **F6.** #10 parks poison messages. They need a way back. | **Manual replay in the GCP console:** not available on the emulator, and not repeatable. | Replayed messages go through the normal dedup (#4). |
| 21 | product | Recording keeps activity forever in v1. | **F15.** It is the system of record, and audit needs the full history. | **TTL with archive:** less storage, but needs an archive store and a retention policy agreed with compliance. | Table growth is unbounded. Partitioning by month is the v2 path. |
| 22 | tech | A risk officer resolves a check with the command `ResolveRiskCheck` (HTTP, served by Segmenter): `checkId`, `decision` (`approve_lower` or `keep_current`), `officerId`, `reason`. Segmenter emits `RiskCheckResolved`, plus `RiskSegmentChanged` when the band is lowered. Notifier alerts on `ManualRiskCheckRequired` and closes that alert on `RiskCheckResolved`. | **F5, F18.** Segmenter owns the band, so it owns the decision to lower it. Notifier only reflects it. | **Emit the check only, resolve in v2:** the check would have no exit, and the merchant stays `high`. **Case-management service:** a new service. Kept for v2. **Notifier closes alerts directly:** the alert and the band could disagree. | Segmenter gains a command endpoint next to its reads (#11). `officerId` is accepted as given until auth lands (v2). It is an audit field, so this is a known gap. After `keep_current`, the next lower recompute opens a new check. |

## 2026-10-18 - design

From the user stories in [domain.md](domain.md).

| # | Kind | Decision | Why | Alternatives considered | Consequence |
|---|---|---|---|---|---|
| 23 | tech | A rule window is anchored at the latest `occurredAt` among the merchant's stored facts. | The same facts must always give the same band. A replayed or late event (#20) must not score the past. | **Processing time:** a replay gives a different band than the first run. **The triggering event's `occurredAt`:** a late old event scores a past moment and can open a wrong check. | Recompute is deterministic and testable without a clock. A late event inside the window counts; one outside it is ignored. |
| 24 | product | Window bounds are inclusive: a fact counts when `occurredAt >= anchor - window`. | Risk teams read "30 days" as including the 30th day. | **Exclusive:** a fact exactly 30 days old drops out one tick early. | Each rule is tested 1s inside, at, and 1s outside the bound (#17). |
| 25 | product | `kyc_expired` has no window. It is never pruned and keeps the merchant `high`. | Expired KYC stays expired until it is renewed. v1 has no renewal type (#18). | **A 30-day window:** the band drops while the KYC is still expired. | Pruning (#6) skips `kyc_expired` facts. Such a merchant never opens a risk check in v1. `kyc_renewed` is v2. |
| 26 | tech | A repeated `activityId` with a different body returns 409. Nothing changes. | A different body under the same id is a client bug. Silent success would hide it. | **Return the original as with an exact repeat:** the client never learns its second fact was dropped. | Recording compares the body on a repeat. An exact repeat still returns the original (#8). |
| 27 | product | Rules run on every event. While a check is open, a lower result updates the check's proposed band and emits nothing. Approval applies the proposed band at that moment. | The officer approves what the check shows now. One drop needs one check and one decision. | **Freeze the proposal when the check opens:** approval gives a stale band, then a second check opens. **Recompute on approval:** no event triggers it, and the result depends on when the officer clicks. **Drop first, officer may override:** limits loosen before anyone looks. #18 rejected this. | A check's proposed band can change while it is open. US5 shows the current proposal. |
| 28 | tech | A rise closes an open check as `superseded` and emits `RiskCheckResolved` with that decision. | Notifier must close the check alert. Without an event, the alert stays open for a check that no longer exists. | **Close silently:** the alert stays open for good. **Notifier infers the close from `RiskSegmentChanged`:** Notifier would hold Segmenter's rule. | `decision` is `approve_lower`, `keep_current` or `superseded`. Only the first two come from an officer. |
| 29 | tech | Segmenter publishes all its events to one topic, `segmenter-events`, with ordering key `merchantId`. Notifier subscribes with `notifier-segmenter-events`. A check alert never reopens once `closed`. | Pub/Sub orders messages only within one topic. With a topic per type, "check closed" can arrive before "check opened", and the alert stays open for good. | **A topic per event type (brief):** no order between types. **Notifier buffers an early close:** every future consumer repeats that logic. | Replaces the brief's `risk-segment-changed` topic. Consumers filter on the event type attribute. A dead-letter replay (#20) can still deliver "opened" after "closed"; the final `closed` covers that. |
| 30 | tech | Each activity type has a strict payload schema: every field required, unknown fields rejected with 422. `chargeback`: `transactionId`, `amount`, `currency`, `reasonCode`. `velocity_breach`: `metric`, `window`, `observed`, `limit`. `kyc_expired`: `kycCaseId`, `documentType`. `failed_login`: `userId`, `method`. No IP address or email. | Recording is the system of record. Bad data must be refused at the edge, not discovered by a later consumer. | **Any JSON object:** no v1 rule reads the payload, but bad facts get stored for good (#21). **Lenient (ignore unknown fields):** typos pass silently. | A new field needs a schema change in Recording first. Field lists live in [domain.md](domain.md) US1. |
| 31 | tech | An `occurredAt` more than 5 minutes ahead of Recording's clock returns 422. | A future time becomes the window anchor (#23) and pushes older facts out of every window. | **Accept any time:** one bad clock can lower a merchant's computed band. **No tolerance:** normal clock skew rejects valid facts. | 5 minutes covers normal clock skew. |
| 32 | tech | A Segmenter fact is keyed by `activityId` and holds only `merchantId`, type and `occurredAt`. It holds no `eventId` and no payload. Refines #6. | `processed_events` already holds the `eventId` (#4). No v1 rule reads the payload (#30). A second copy of either needs a reason, and neither has one. | **Keep `eventId` on the fact (#6 as written):** the same id in two tables. **Copy the payload:** a second store of client data with no reader. | A rule that reads the payload needs a schema change in `facts` and a replay (#20). |
| 33 | tech | No service calls another over HTTP. Every arrow between services is a copy carried by an event. | The brief has services react only to events. Every ask ties the caller to the owner's uptime. | **Notifier asks Segmenter for check status on read:** the alert list fails while Segmenter is down. | Each service stays up on its own. The cost is lag: I12 and I15 are eventual. |
| 34 | tech | Notifier keeps one `alerts` table with a `kind` column. `check_id` is set only for `risk_check_required`. | US9 lists both kinds together, newest first. One table answers that with one query. | **A table per kind:** a union on every read. | The unique key on `check_id` ignores rows where it is empty. |
| 35 | tech | The replay command reads a dead-letter subscription and republishes each message to its source topic. It keeps the `eventId`, attributes and ordering key, and acks the dead-letter copy only after the publish is acked. | The `eventId` must stay the same, so dedup (#4) still works. | **A retry topic per subscription:** more topics, and other subscribers never see the fix. **New `eventId` on replay:** a consumer that already applied it applies it again. | Every subscription on that topic receives the message again. Each one drops it by `eventId` if already applied. |
| 36 | tech | Each service connects as its own Postgres role, with rights only on its own schema. Recording's role may insert and select `activities`, never update or delete. | "Each service owns its own data" then holds in the database, not only in code review. It also guards I2. | **One shared role:** isolation rests on code review alone. **A database per service:** stronger, but the brief allows one database with a schema per service. | A test proves that Segmenter's role cannot read `recording.activities`. |
| 37 | tech | In v1, the dead-letter alert of #10 is a `dead-letter-monitor` container. Every 60 s it reads each dead-letter subscription's depth and logs at `ERROR` when it is above 0. | v1 has no monitoring stack (#16). A log line at `ERROR` is what an operator watches in Compose. | **Route it through Notifier:** Notifier would consume infrastructure signals, which is not its job. **Cloud Monitoring alert:** needs GCP. That is the v2 path. | One more container. In v2, a Cloud Monitoring alert on the same depth replaces it. |
| 38 | tech | Pruning is per type: a fact is deleted once it is older than `anchor - window` of its type's rule. `kyc_expired` is never deleted. | A merchant under attack sends thousands of failed logins. They matter for 1 hour, not 30 days. | **Prune everything at the longest window (#6):** 30 days of failed logins load on every event. | The facts kept per merchant are bounded by the rule windows. Policy v2 with a longer window needs a replay (#20) to restore facts already pruned. |
| 39 | tech | A policy version is data: a list of rules (type, count, window, band) and a number. Segmenter counts facts per rule window in one SQL query. The domain picks the band from the counts (policy-v1.md P3). | Loading every fact to count it in Python does not scale for a hot merchant. Rules as data keep the domain testable without a database. | **Load facts, count in Python:** simple, but cost grows with facts per merchant. **Rules as code per version:** more freedom, but a weighted score would need a different interface anyway. | The count query is the only place that reads `facts` for a decision. Its result is tested against P2's boundaries. |
| 40 | tech | Outbox rows are deleted 7 days after `sent_at`. `processed_events` rows are deleted after 14 days. A cleanup runs inside each relay or worker every hour. | Both tables otherwise grow forever. 14 days exceeds the 7-day dead-letter retention, so a replayed event is still recognised. | **Keep forever:** unbounded growth and a slower relay index. **Delete outbox rows on send:** no trail to debug a lost event. | An event replayed after 14 days is applied again. Segmenter is still safe: facts are keyed by `activityId` (#32). |
| 41 | product | `docs/policy-v1.md` is the single reference for the segmentation rules. Code and tests cite its section ids. It replaces the deferred "policy doc". | The rules were spread across ten decisions and the plan. A reader of the code needs one page to check it against. | **Rules stay in decisions and the plan:** nothing to cross-reference. **A full rule-engine doc:** too much for five thresholds. | A rule change updates `policy-v1.md` first, then code. A new version gets its own file. |
| 42 | tech | Three aggregates: `Segment` (full), `Activity` and `Alert` (thin, one entity each, `Alert` covers both kinds). One unit of work per use case, with an explicit commit. At commit, the unit of work moves the roots' events into the outbox in raise order. The outbox and `processed_events` belong to the unit of work. A version conflict reruns the use case up to 3 times with backoff, then the worker nacks and the API returns 503. Ack, reply and the alert log line happen after commit. Detail in [aggregates.md](aggregates.md) A1-A6. | An aggregate is a consistency boundary that owns its rules, and only `Segment` has rules that span several objects. With the outbox inside an aggregate, the relay and cleanup (#40) would write many aggregates at once, and cleanup would break I3 and I11. | **Outbox inside the aggregate:** the relay would take each merchant's version, and cleanup could never run. **Nack on the first conflict:** a failed-login burst dead-letters valid events (#10). **Full roots everywhere:** extra layers in Recording and Notifier, with no rule spanning objects there. **`segment_changed` alerts as plain data:** a write path that bypasses every root. **Log before commit:** a rolled-back alert would still be logged. | Handlers only load a root, call one method and commit. Unit tests use a fake unit of work. A crash after commit can lose the alert log line, but never the alert row. |
| 43 | tech | Every consumer is built for at-least-once delivery with no order guarantee. A message can arrive twice, late, or before an earlier one. The ordering key (#9) stays as a best-effort hint. Refines #9 and #10. | Pub/Sub promises at-least-once delivery only. Per-key order is best-effort, weaker with a dead-letter topic, and the emulator does not keep it after a nack. | **Rely on per-key order:** not guaranteed, and untestable on the emulator. **Hold the key in our own code:** rebuilds what the broker only approximates. | Dedup by `eventId` (#4), the version number (#9) and recompute from stored facts (#23) carry correctness. Tests deliver duplicates and out-of-order events. The emulator check proves dead-lettering only. |
| 44 | product | A recompute that gives the current band closes an open check as `superseded` and emits `RiskCheckResolved`, as a rise does. With no open check, an equal band still changes nothing. Refines #28 and policy P4. | An open check proposes a band below the current one. When the rules come back to the current band, the proposal is stale. #27 does not recompute on approval, so approving it would set the band below the rule band and break I6. | **409 on approval when the proposal is below the rule band:** changes #27, and the officer gets an error on a check that still looks valid. **Set the proposal to the rule band:** a check that proposes no change. | The officer never sees a stale question. A check can close without an officer, on a rise or an equal band. |

## Deferred to v2

- Deploy target (Cloud Run is the candidate).
- Infra as code (Terraform).
- Auth on the HTTP APIs.
- Tracing across services (OpenTelemetry, with trace context in the message attributes).
